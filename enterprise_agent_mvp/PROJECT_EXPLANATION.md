# 企业知识库问答与工单协同 Agent - 项目说明

## 1. 这个项目是做什么的

这个项目模拟了一个企业内部支持 Agent，它可以：

- 结合知识库回答问题
- 在回答过程中调用工具
- 创建和升级工单
- 在 `OpenAI兼容接口` 与 `Anthropic接口` 之间切换

它适合用来展示下面这些 AI 应用开发能力：

- 大模型 API 接入
- Provider 抽象
- Agent Loop 设计
- Tool Calling
- 轻量级 RAG
- 简单持久化能力

## 2. 整体架构

项目被拆成了几块清楚的小模块，每一块职责单一，方便阅读和讲解。

### `app/providers/`
这一层是**模型提供方兼容层**。

- `base.py`：定义统一的 `LLMProvider` 接口
- `openai_compatible.py`：适配 OpenAI 风格的兼容接口
- `anthropic_provider.py`：适配 Anthropic 的 messages API
- `factory.py`：根据配置创建对应的 provider

**这一层的意义：**  
Agent 主流程不直接和具体平台耦合，后面如果要换 provider，只需要换适配器，不需要重写业务逻辑。

### `app/agent/`
这一层是**Agent 主循环**。

- `engine.py`：负责发送消息、接收模型输出、判断是否需要工具调用、执行工具并继续下一轮

**这一层的意义：**  
这是整个项目最核心的部分，它让项目从“普通聊天”变成了“可以执行动作的 Agent”。

### `app/rag/`
这一层是**检索增强**。

- `retriever.py`：负责加载本地知识库文本，并进行轻量级检索

**这一层的意义：**  
项目不会直接让模型“瞎答”，而是先从知识库里取相关信息，再把结果交给模型组织回答。

### `app/db/`
这一层是**工单持久化**。

- `ticket_repository.py`：基于 SQLite 存储工单，并提供创建、查询、升级等方法

**这一层的意义：**  
这样未解决的问题不会只停留在一段文本里，而是能沉淀成结构化工单。

### `app/tools/`
这一层是**工具能力层**。

- `ticket_tools.py`：定义暴露给模型的工具规格，并把工具调用映射到 Python 函数

**这一层的意义：**  
它连接了“模型推理”和“业务操作”，是 Tool Calling 的落地点。

## 3. 一次请求是怎么走的

下面是 `/chat` 的基本流程：

1. 用户向 `/chat` 发送问题
2. FastAPI 调用 `AgentEngine.run(...)`
3. Agent 把当前消息历史交给 provider
4. provider 返回：
   - 普通文本回答
   - 或一个/多个工具调用请求
5. 如果需要工具：
   - Agent 调用对应 Python 工具函数
   - 把工具结果加入消息历史
   - 再次请求模型
6. 如果模型不再请求工具，就返回最终答案

## 4. 为什么要做 Provider 抽象

这是这个项目最值得讲的点之一。

### OpenAI 兼容接口
通常会返回：

- `message.content` 中的回答文本
- `message.tool_calls` 中的工具调用

### Anthropic 接口
通常会返回：

- `content` 数组中的文本块
- `tool_use` 类型的工具请求
- 后续还要通过 `tool_result` 反馈工具执行结果

### 本项目的处理方式

虽然它们对外协议不同，但我在内部统一成了：

- `AssistantResponse`
- `ToolRequest`
- `CanonicalMessage`

这样主流程只处理统一结构，不直接依赖某个平台的格式细节。

## 5. 为什么它算 AI 应用开发项目

这个项目不是做模型训练，也不是做算法研究。  
它更偏向**AI 应用开发**，因为它关注的是：

- 如何接模型 API
- 如何设计 Agent Loop
- 如何把模型输出接到工具和业务流程
- 如何做基础检索增强
- 如何兼容不同模型提供方

这类能力恰好是很多实习岗位更想看到的。

## 6. 这个项目故意保持轻量的地方

为了让项目容易跑通、容易解释、容易写进简历，这版有意保持轻量：

- 检索器用的是词项重叠打分，不是 embedding
- 没有做前端页面
- 没有加认证系统
- 没有做日志追踪平台
- 没有做评测可视化

这不是缺点，而是 **MVP 项目合理控制复杂度** 的结果。

## 7. 面试里最值得讲的内容

如果面试官问这个项目，你最值得围绕这些点展开：

1. 为什么要做 `LLMProvider` 适配层
2. 为什么 Agent 不能只输出文本，还要能调工具
3. 为什么先检索再回答，比直接生成更稳
4. 为什么工单系统能让项目更像真实业务场景
5. 为什么这个项目比“普通聊天机器人 demo”更像 AI 应用开发

## 8. 后续可以怎么继续扩展

这个项目后面很自然可以继续往下做：

- 把轻量检索替换成 embedding + 向量库
- 增加工单更完整的状态流
- 增加评测数据集和结果统计
- 增加用户鉴权
- 增加日志与调用追踪
- 增加简单 Web 前端

如果你在面试里说出这些扩展方向，会显得你不仅会搭 MVP，也理解它下一步该如何进化。
