# 企业知识库问答与工单协同 Agent - 面试问题整理

## 1. 为什么要做 Provider 抽象层？

因为 Agent 主流程不应该依赖某一家模型平台的协议细节。  
OpenAI 兼容接口和 Anthropic 接口在消息格式、工具调用格式、工具结果回传方式上都有差异。  
通过统一 `LLMProvider` 接口，我把这些差异封装在适配层里，让 Agent Loop 只处理统一结构。

## 2. 为什么这个项目不只是一个聊天机器人？

因为它不只是“问一句答一句”。  
它有：

- 检索增强
- 工具调用
- 工单创建与升级
- 多轮流程控制

也就是说，它可以把“文本问答”升级成“业务流程的一部分”。

## 3. 为什么这里要做 RAG？

因为很多企业支持场景里，模型不能只靠参数记忆来回答。  
需要先去查公司知识库，再基于检索结果组织回答，这样更可靠，也更符合企业问答的实际需求。

## 4. 为什么你的 RAG 先做成轻量版？

这版项目的目标是做一个容易跑通、容易解释、容易测试的 MVP。  
所以检索层先用轻量方式实现，把结构跑通。  
如果继续升级，我会换成 embedding + 向量数据库。

## 5. OpenAI 兼容接口和 Anthropic 接口的主要区别是什么？

主要区别在：

- 消息格式不同
- 工具声明格式不同
- 工具调用结果回传方式不同

OpenAI 兼容接口通常把工具调用放在 `tool_calls` 里；  
Anthropic 会返回 `tool_use`，然后要求后续通过 `tool_result` 再送回去。  
我在项目里把它们统一归一化成内部结构来处理。

## 6. 为什么这里要用 SQLite？

因为 SQLite 足够轻量，很适合 MVP。  
它能让项目具备“有状态”的能力，比如把未解决问题保存成工单，而不是一次回答后就丢失上下文。

## 7. 这个项目里最关键的能力点是什么？

我会认为有 4 个：

1. 大模型 API 接入  
2. Agent Loop 设计  
3. Tool Calling 与业务流程串联  
4. Provider 兼容层抽象

这 4 点组合起来，才让项目变成一个真正的 AI 应用原型。

## 8. 如果继续做下去，你最先会补什么？

我会优先补：

- embedding 检索
- 评测样例和效果验证
- 更完整的工单状态流
- 日志和调用追踪

因为这些会直接提升项目的稳定性、可解释性和展示价值。

## 9. 你在类似项目中能承担什么工作？

我可以承担这些工作：

- 模型 API 接入
- provider 切换与适配
- Agent Loop 主流程编排
- 工具调用设计
- 本地环境配置
- 原型搭建与运行验证
- Prompt 调整和结果优化

这也是为什么这个项目很适合放在 AI 应用开发实习简历里。
